# CasePilot 测试设计质量 Skill

## 在 CasePilot 中的职责

- 当前需求解析模型只抽取原文明确表达的需求事实，并按既定 `StructuredRequirement` JSON 契约输出；不生成测试点、测试用例、步骤或预期结果。
- 规则引擎只消费标准化事实并确定性地生成测试点和用例。不要让模型或 Skill 绕过该边界。
- 需求原文是产品行为的唯一证据。Skill 中的检查模式是风险提示，不是产品规则。

## 识别原文信息

- 抽取可验证的功能、行为、业务规则和流程步骤；同一句有多个独立条件时，拆成最小、仍可由原文引用支持的事实。
- 不要把需求标题、章节名、表格排版残留、模块标签、背景动机、历史说明或“需算法支持”等责任描述当作产品行为。
- 精确保留原文中的阈值、比较关系、单位、状态前提、时间窗、触发动作和适用对象；不要把“有变化时”“24 小时内”等条件泛化或互相替换。
- `待定`、`待确认`、`可能`、`待讨论`等表述不是已确认的通过/失败规则。将原文和引用放入 `openQuestions`，单独提示测试人员确认是否有特殊逻辑、适用范围或前置条件；不得把它们伪装成普通事实或据此生成确定预期。
- 事实必须带能在输入原文中逐字定位的引用。没有直接依据就不输出；不要补常识、隐含前提或实现方案。

## 当前阶段的设计范围

- 本阶段只处理需求原文明确表达的行为、待确认项和可确定的描述冲突，不扩展隐性风险检查清单。
- 对未写明的账号隔离、跨设备、权限、缓存、并发等测试经验，不要自行补成事实或测试点，也不要现在将其沉淀为 Skill 规则。后续应在更多需求评测中反复观察、抽象和评审后再决定是否加入。
- 发现语义上无法同时成立的明确规则时，保留冲突各方及其原文引用，在测试点和用例上标记 `needsProductConfirmation` 与 `conflict_ids`；用例应提醒向产品确认，不得给出冲突规则的通过/失败预期。
- `openQuestions` 与 `conflicts` 是独立于正式 `facts` 的输出；它们不能被计入已确认需求覆盖率。

## 条件冲突与质量检查

- 不要自行选择冲突规则的其中一版。将冲突及其来源留给人工澄清；确认后再更新需求基线和回归期望。
- 对解析结果检查：背景和标题没有混入事实；阈值、状态、时间窗和触发条件没有丢失；每条事实可追溯到原文；待确认项没有被定成确定规则；冲突输出保留各方依据并标记关联测试点。
- 对正式测试用例检查：前置条件、操作步骤具体可执行，预期结果可观察且能映射到已确认事实；不要用“符合需求原文”作为预期。

## 演进规则

- 不因一两个案例就扩充隐性测试经验。后续积累足够多、彼此独立的需求样本后，再评估是否将重复出现且可复用的模式沉淀为检查项，并记录适用范围、依据和版本。
- 每次修改 Skill 都运行使用合成输入的 golden 回归，检查明确需求覆盖、解析准确性、误报、步骤可执行性、预期可验证性及追溯性。项目测试、文档和 Skill 不应固化真实客户需求或手工用例；只沉淀经抽象的可复用模式。
- Skill 建议和产品规则分开维护。只有经产品确认的业务行为才能进入确定性规则与正式覆盖率。
