# CasePilot 技术架构

## 核心流程

```text
需求文档 / 设计文档
        |
        v
文档解析层（提取文本与元数据）
        |
        v
需求读取模型（抽取原文事实与精确引用）
        |
        v
原文引用校验 + 需求结构标准化
        |
        v
确定性规则引擎（测试点、测试用例、步骤、预期结果）
        |
        v
人工评审与编辑 -> Excel / XMind 导出
```

## 固定数据契约

当前领域契约以 `src/domain/model-contract.js` 的 JSDoc 和运行时校验为准，服务端通过 `server/schemas.js` 暴露统一入口：`StructuredRequirement` 为 `1.0.0`，`TestPlan` 为 `2.0.0`。测试点和用例均必须包含非空 `fact_ids` 与 `rule_version`，且后者必须与方案级 `ruleVersion` 一致。字段名、枚举、空值表达和数组形状都是契约的一部分；未知字段会被拒绝。事实中的可选语义标量统一使用 `null`，列表统一使用空数组，追溯对象始终包含文档 ID、章节、原文引用和半开区间偏移。

模型原始输出属于候选抽取结果，不是 `StructuredRequirement`。标准化器会验证来源并投影为固定契约；规则引擎入口校验版本化需求对象，生成方案后也校验 `TestPlan`。变更字段、枚举或语义必须同步更新 JSDoc、标准化器/生成器、契约断言，并提升对应 schema 版本；不同 schema 版本不可静默混用。`TestPlan` 中的 `provider`、`modelId`、`options` 是运行元数据，变化不应影响相同事实与规则版本下的测试点和用例内容。

模型只参与“需求读取”这一层。它不负责提出测试点，不生成测试用例、步骤或预期结果，也不参与风险建议生成。Provider 的输出是带有原文引用的结构化需求事实；引用校验失败的事实会被丢弃，完全没有可追溯事实时请求失败。模型输出不能直接作为最终测试方案。

## 分层职责

### 1. 输入与文档解析层

接收文本、Markdown、DOCX、PDF 或设计说明，负责提取文档文本和基本元数据。当前 MVP 接受粘贴文本，DOCX/PDF 解析仍待接入。

### 2. 需求读取层

通过统一 Provider 接口选择百炼、其他兼容模型或 Mock。模型仅输出候选 `facts` 和原文引用；同一句可以拆成多个候选项，候选的粒度与 `rule_type` 只作为读取提示。标准化器负责定位原文句段、按固定规则拆分可独立识别的事实、从原文重新判定规范 `rule_type`、归一字段并去重，最后输出统一的 `StructuredRequirement.facts`。模型标签不会直接改变规则引擎的输入。

该一致性保证针对“模型引用到了同一原文句段”的情况；若某个模型完全漏掉一段，当前标准化器不会凭空补回。若后续要求不同模型对整份文档也得到相同的完整事实集，需要增加独立于模型的全文候选句扫描，或明确接受模型召回率差异作为需求读取质量的一部分。

模型质量比较应关注事实抽取的准确率、召回率、字段与规则分类准确率、引用精确率和重复事实率。比较不同模型不能让它们各自生成用例，否则无法区分解析质量与测试设计策略的差异。

### 3. 确定性测试设计层

`server/rule-engine.js` 是唯一的测试点和用例生成入口。它将标准化事实按规则类型映射到固定模板，例如必填、禁止、最小值、最大值、范围、枚举、频率、状态转换和权限规则。范围规则样板由固定事实生成一个测试点及四个边界用例；黄金 fixture 对完整输出深度断言。测试内容应当由事实、规则版本和明确的生成选项决定，不调用任何模型。

规则引擎需要为每个测试点和用例保留需求事实 ID 与原文追溯信息。对于信息不足、不能安全推出具体边界的规则，应采用明确标记的通用模板或跳过边界推导，不得自行补造业务约束。规则变更应有版本号，并通过固定输入/输出的回归测试评审。`test/server.test.js` 对两个 schema 的版本、精确字段集合、枚举以及标准化结果做契约断言，防止模型切换或实现调整造成结构漂移。

同一结构化需求、规则版本和生成选项应产生一致的测试点与用例内容。方案记录规则引擎版本，以便对比模型输出时区分规则变化。计划 ID 和创建时间等运行元数据可以不同，但不应改变内容。

### 4. 评审与交付层

人工评审可修订规则生成结果；导出层基于同一 `TestPlan` 支持多个组织模板。Excel 面向用例评审和执行，XMind 面向测试点讨论。列名、分组、节点层级和追溯字段等单位差异由导出配置表达，不由模型决定。

## 可追溯指标

当前页面的“需求事实映射率”指标准化后且有有效原文引用的需求事实中，至少映射到一个规则测试点的比例。它不等于需求整体覆盖率，也不衡量需求文档中尚未被模型抽取的内容。指标计算应以解析后的事实集为分母，并在后续实现中通过事实 ID 的关联关系统计，避免把常量 100% 误解为测试充分性证明。

## 多模型调试

后续增加模型实验能力时，对同一输入文档比较不同模型的结构化需求结果，记录：

- 输入文档版本与解析后的文本版本
- Provider、模型名称、提示版本和生成参数
- 模型原始抽取结果与标准化结果
- 每项事实的引用校验结果及人工标注
- 抽取准确率、召回率、引用精确率、重复率和错误类型

选定一份规范化需求结果后，再交给同一个规则引擎生成测试方案。这样评估只反映模型读取需求的差异，测试用例则由共享规则稳定地产生。
