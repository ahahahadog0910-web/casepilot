# CasePilot 项目阶段大纲

本文档是 CasePilot 的阶段执行基线。后续新增功能、调整架构和接入模型时，必须先确认所属阶段、阶段目标和验收条件，再实施对应工作。

## 一、项目目标与边界

CasePilot 的目标是将需求文档或设计文档转换为可评审、可追溯的测试点和测试用例，并支持按不同交付规则导出 Excel 和 XMind。

平台采用以下固定边界：

```text
文档输入
  -> 文档解析
  -> 模型需求读取
  -> 引用校验与需求标准化
  -> 确定性规则引擎
  -> 人工评审与修订
  -> Excel / XMind 导出
```

- 模型只负责从原文中读取和抽取明确事实，不生成测试点、测试用例、步骤或预期结果。
- 标准化器负责统一不同模型的输出结构、引用、事实粒度和规则类型。
- 规则引擎负责确定性地生成测试点和测试用例。
- 导出格式、字段和节点层级由模板或组织配置决定，不由模型决定。
- 真实需求和手工测试用例只作为项目外部验证材料，不写入项目源码、文档、Skill、fixture 或正式回归数据。
- 项目中只保留经过抽象的通用规则、合成输入、合成期望输出和可复用质量检查。

## 二、执行纪律

### 1. 阶段顺序

阶段必须按顺序推进。当前阶段的退出条件全部满足后，才能进入下一阶段。跨阶段开发需要先补充阶段决策记录和影响范围说明。

### 2. 每次变更必须回答的问题

每个功能或修复在实施前后都要明确：

1. 属于哪个阶段和哪个能力边界。
2. 是否会改变 `StructuredRequirement`、`TestPlan` 或导出契约。
3. 是否会改变规则引擎输出或规则版本。
4. 是否需要新增合成回归输入和手写期望输出。
5. 是否会把模型职责、规则职责或人工评审职责混在一起。
6. 是否会把真实需求信息带入项目资产。

### 3. 统一完成标准

任何阶段都必须同时具备以下结果，才算完成：

- 代码或文档实现已落地。
- 有针对性的自动化验证已通过。
- 关键输入、输出和版本信息可追溯。
- 已更新项目文档和变更说明。
- 未引入真实业务案例、客户信息或无法复用的专有规则。

### 4. 失败处理

如果某阶段验收失败，应回到该阶段修复，不通过增加后续阶段的临时逻辑绕过问题。无法确定的产品规则必须进入“待确认项”，不得被规则引擎当作已确认事实生成正式用例。

## 四、各阶段目标与验收条件

### 阶段 0：范围与架构基线

目标：确定平台的核心职责和技术边界，防止后续把模型、标准化器、规则引擎和导出层混为一体。

工作内容：

- 明确模型只参与需求读取。
- 冻结 `StructuredRequirement` 和 `TestPlan` 的字段、枚举、空值表达和版本策略。
- 明确事实必须带原文引用，测试点和用例必须带 `fact_ids`、`rule_version` 和追溯信息。
- 确定 Provider、标准化器、规则引擎和导出层的接口边界。
- 建立项目 Skill，并规定建议项、待确认项和已确认事实的边界。

阶段成果：

- 版本化 schema 和运行时校验。
- Provider 与规则引擎的职责说明。
- 项目 Skill。
- 架构文档和基础测试。

验收条件：

- 未知字段、错误版本、非法枚举和缺失追溯信息会被拒绝。
- 模型输出不能直接绕过标准化器进入规则引擎。
- 规则引擎不依赖模型输出测试点或用例。

### 阶段 1：确定性核心链路

目标：建立第一条可运行、可复现、可追溯的转换链路。

工作内容：

- 使用固定合成事实验证规则模板。
- 实现范围、最小值、最大值等基础边界规则。
- 输出测试点、前置条件、步骤、预期结果和追溯字段。
- 为测试点和用例写入非空 `fact_ids` 和统一 `rule_version`。
- 建立手写 golden 期望输出，并对完整结构做深度断言。

阶段成果：

- “固定事实 → 固定测试点 → 固定用例”的可运行样板。
- 规则引擎单元测试和端到端测试。
- 规则版本和内容稳定性验证。

验收条件：

- 相同事实、相同规则版本和相同选项产生相同的测试点和用例内容。
- 测试点和用例均能反查到事实 ID和原文引用。
- 预期结果是可观察、可判定的内容，不是需求原文复述。
- 模型 Provider、模型名称变化不会改变规则引擎生成内容。

### 阶段 2：需求标准化质量

目标：让不同模型对同一原文的候选输出，经过标准化后尽可能进入一致的事实集合。

工作内容：

- 排除标题、背景、说明、排版残留和责任描述等非需求内容。
- 将模型候选事实按原文引用重新定位和校验。
- 按固定规则拆分最小可判定事实，并进行去重和字段归一。
- 识别并保留阈值、比较关系、单位、状态、时间窗、触发动作和适用对象。
- 处理待定、待确认和冲突规则，避免将其伪装成确定事实。
- 保留事实到原文的精确偏移和多处引用。

阶段成果：

- 标准化器规则说明。
- 合成输入回归集，覆盖标题、背景、阈值、状态、时间和条件组合。
- 解析准确性、误报、漏报、重复和引用精度测试。
- 待确认项和建议项的独立数据结构设计，或明确暂不进入正式输出。

验收条件：

- 标题和背景不会进入正式事实集合。
- 关键阈值、状态和时间条件不会在标准化过程中丢失。
- 没有原文依据的内容不会进入 `facts`，也不会计入需求覆盖率。
- 同一合成原文在不同候选粒度下能得到一致的规范事实。

### 阶段 3：多模型实验与评测

目标：在相同标准化器和规则引擎下，比较不同模型的需求读取质量。

工作内容：

- 接入 Mock、百炼及其他兼容模型 Provider。
- 保存 Provider、模型名称、提示词版本、参数、输入文档版本和原始响应元数据。
- 对同一输入运行多个模型，并分别保留原始候选结果与标准化结果。
- 建立合成 golden 评测集和人工标注格式。
- 分析事实召回率、准确率、引用精度、规则分类准确率、重复率和错误类型。

阶段成果：

- 模型实验记录结构。
- 模型对比页面或接口。
- 可重复的批量评测脚本。
- 模型选择报告模板。

验收条件：

- 不同模型使用同一规则引擎生成后续测试方案。
- 模型差异能定位到事实抽取结果，而不是用例生成策略差异。
- 每次实验可以复现输入、配置、原始输出和标准化结果。
- 不能用未经标注的真实需求直接作为项目内 golden 数据。

### 阶段 4：文档接入与项目管理

目标：让用户可以稳定地输入、保存和再次处理需求文档。

工作内容：

- 支持 Markdown、TXT 等文本输入。
- 接入 DOCX、PDF 等文档解析，并保留页码、段落或节点等来源元数据。
- 建立项目、需求文档、解析任务、测试方案和版本关系。
- 支持文档版本和解析结果版本。
- 增加任务状态、错误信息和重复执行控制。

阶段成果：

- 文件上传和文本解析接口。
- 文档及任务数据模型。
- 文档版本与需求事实追溯关系。
- 解析失败和重试机制。

验收条件：

- 同一文件版本可以重复解析并得到可比较结果。
- 解析失败不会生成伪造的事实或测试方案。
- 原文定位信息在后续评审和导出中仍然可用。

### 阶段 5：评审与编辑工作台

目标：让用户能够在生成后审阅、确认和修订结果，并保留修改依据。

工作内容：

- 展示原文、结构化事实、测试点和用例之间的关联。
- 支持事实确认、事实驳回、事实拆分和事实合并。
- 支持测试点和用例的人工编辑、状态标记和备注。
- 区分模型抽取结果、规则生成结果和人工修改结果。
- 提供待确认项和风险建议的独立视图。

阶段成果：

- 评审工作台。
- 修改记录和审计信息。
- 重新生成策略：明确哪些修改触发局部重算，哪些修改需要整体重算。
- 人工确认结果可用于后续模型评测和规则改进。

验收条件：

- 人工修改不会丢失原始事实和原文引用。
- 规则重新生成不会无提示覆盖人工确认内容。
- 正式测试用例的每个关键预期都能回溯到事实或人工确认记录。

### 阶段 6：Excel 与 XMind 交付

目标：提供可直接交付给不同评审和执行团队的标准文件。

工作内容：

- 将当前导出能力升级为标准 XLSX 文件生成和校验。
- 建立 XMind 节点树模型和导出校验。
- 为 Excel 定义测试点、前置条件、步骤、预期、优先级、状态和追溯字段。
- 为 XMind 定义根节点、分类节点、测试点节点和可选追溯信息。
- 支持导出模板版本和导出配置。

阶段成果：

- XLSX 导出器。
- XMind 导出器。
- 导出模板和字段映射配置。
- 导出文件结构回归测试和可打开性验证。

验收条件：

- 导出文件可以被目标工具正常打开。
- 导出内容与评审工作台中的 `TestPlan` 一致。
- 导出失败会明确报错，不产生半成品文件。
- 格式差异不会改变事实、测试点和用例的语义。

### 阶段 7：组织规则与模板

目标：支持不同单位对 Excel 和 XMind 的字段、分组和审阅习惯。

工作内容：

- 把列名、列顺序、节点分组、节点层级、状态值和是否包含建议项配置化。
- 建立模板版本和适用项目范围。
- 支持默认模板、组织模板和项目级覆盖。
- 增加模板校验，防止配置导致追溯字段丢失。

阶段成果：

- 模板配置 schema。
- 模板管理接口和页面。
- 至少两套合成组织模板的导出回归测试。
- 模板升级和兼容策略。

验收条件：

- 同一 `TestPlan` 可生成不同格式的交付文件。
- 模板变化不会改变核心测试语义。
- 必需字段、事实 ID、规则版本和来源追溯不可被模板删除。

### 阶段 8：稳定性与上线准备

目标：使平台具备长期运行和多人使用的基础能力。

工作内容：

- 增加鉴权、权限、敏感配置保护和日志脱敏。
- 建立模型调用超时、重试、限流和费用统计。
- 增加任务队列、缓存、并发控制和大文档处理策略。
- 建立接口监控、错误追踪、审计日志和数据备份。
- 完成部署、回滚和版本发布流程。

阶段成果：

- 运行环境配置说明。
- 监控和告警指标。
- 性能、安全和故障恢复报告。
- 发布检查清单。

验收条件：

- 模型不可用时，系统能明确失败或切换到允许的 Provider。
- 任务重试不会产生重复或互相覆盖的正式结果。
- 敏感配置和用户文档不会出现在普通日志中。
- 版本升级可以回滚，且 schema 与规则版本关系明确。

## 五、当前执行位置

当前项目处于“阶段 1 已完成样板、阶段 2 正在建设”的状态：

- 已有版本化 `StructuredRequirement` 和 `TestPlan` 契约。
- 已有 Mock 和 OpenAI 兼容 Provider 接口。
- 已有确定性规则引擎和范围规则 golden 回归。
- 已有项目级测试设计 Skill。
- 当前优先工作是继续提升标准化器对通用条件、阈值、状态和时间约束的识别质量，并用合成回归数据验证。

在阶段 2 验收前，不进入新的真实模型横向评测，也不扩展复杂导出和组织模板功能。这样可以先保证不同模型进入规则引擎前使用稳定、可比较的事实结构。

## 六、每阶段固定交付清单

每个阶段结束时必须提交以下材料：

1. 阶段实现说明：做了什么，为什么做，影响哪些接口。
2. 变更文件清单：代码、schema、文档、测试和配置。
3. 验收记录：运行的命令、通过结果和未解决问题。
4. 回归数据说明：新增的合成输入、期望输出和覆盖的风险。
5. 版本记录：schema 版本、规则版本、提示版本或导出模板版本。
6. 下一阶段入口条件确认。

真实需求的评测结果可以在项目外单独保存和讨论，但不作为上述项目资产提交。

## 七、变更控制

以下变更必须先更新本大纲或补充决策记录，再改代码：

- 让模型参与测试点或测试用例生成。
- 修改 `StructuredRequirement` 或 `TestPlan` 的语义和字段。
- 改变规则引擎的输入边界或确定性要求。
- 将建议项、待确认项直接纳入正式覆盖率或正式用例。
- 新增一个组织专属业务规则并写入通用规则层。
- 改变 Excel、XMind 的核心交付语义。
- 将真实需求、客户信息或手工测试用例提交到项目仓库。

遇到上述情况，先记录影响范围、替代方案、回归计划和版本变化，再实施。
