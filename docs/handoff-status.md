## 必须遵守的逻辑规则

| 规则 | 执行要求 |
| --- | --- |
| 职责分层 | 模型仅读取需求并输出候选事实；标准化器校验原文引用、做确定性拆分、归一和去重；规则引擎负责所有测试点、步骤和预期生成。 |
| 原文是产品行为证据 | 需求标题、章节名、背景动机、版式残留、职责描述不自动成为事实。没有原文依据的内容不能进入已确认事实或确定性用例。 |
| 事实粒度与语义 | 最小化事实时保留阈值、运算关系、单位、状态、时间窗、触发动作、适用对象及来源引用；不同模型对同一被引用内容的输出经标准化后应尽量一致。 |
| 不确定项 | “待定/待确认/可能/待讨论”等内容进入 `openQuestions`，独立提醒测试人员确认特殊逻辑、范围和前置条件；不得计入已确认事实覆盖率或生成确定通过/失败结论。 |
| 描述冲突 | 保留冲突双方和各自引用，关联测试点/用例标记 `needsProductConfirmation`、`conflict_ids`；不自行选择一方，也不输出伪确定预期。 |
| Skill 的使用边界 | `.cursor/skills/casepilot-test-design/SKILL.md` 是解析与质量提醒，不是产品规则。账号隔离、跨设备、缓存等原文未提出的风险，不得仅凭 Skill 生成正式事实/用例。隐性经验应等更多独立需求中反复观察、抽象评审后再考虑沉淀。 |
| 测试用例质量 | 步骤必须可执行，预期必须可观察、可判定并对应已确认事实；不能用“符合需求原文”代替实际预期。信息不足时明确标草稿/待确认。 |
| 稳定契约与版本 | 修改 `StructuredRequirement` / `TestPlan` 必须同步更新 JSDoc、运行时校验和契约测试并提升 schema 版本。改变测试生成行为需更新规则版本、手写 golden 输出和回归测试。 |
| 真实案例保密 | 真实需求和手工用例只作为本地、项目外验证材料。项目内只保留经抽象的通用模式、合成输入和手写合成期望。 |

## 新对话建议启动方式

在 CasePilot 项目中开启新对话后，可直接发送：

> 请先阅读 `docs/handoff-status.md`、`docs/project-roadmap.md` 和 `docs/architecture.md`。从 P0“完成 2.2.0 真实案例验证与人工测试点对比”继续：使用我之前提供的需求文档和对应手工测试点，只在项目外做对比，不要把真实业务内容写入项目；先确认文件可访问，再生成并检查 XMind 测试点，最后给出差距分析和可抽象为合成回归的优化建议。

如果新对话无法访问旧对话附加的本地文件，请重新附上需求文档和手工整理的测试点文件。文件名在之前对话中出现过不同版本，需以用户本次确认的文件为准。
